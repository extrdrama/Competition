一、作品概述

一句话：凭迹（CredWatch）是一套面向防御目的的平台，持续监测 15 类公开渠道

（代码托管平台、容器镜像仓库、软件包仓库、Paste 分享站点、Wiki 知识库、App 与小程序等），

自动发现其中暴露的云上凭据（AccessKey/SecretKey、API Token、数据库连接串、SSH 私钥、

OAuth Client Secret、支付商户密钥等），并将"凭据从公开暴露到被责任主体感知"的时间窗口

从行业常见的数天至数月，压缩到分钟级。

解决的核心问题：云上凭据一旦泄露，攻击者能以"合法身份"访问资源，绕过绝大多数

传统安全防护。而现有方案要么只能扫描单个代码仓库（覆盖不了公开渠道），

要么只报"疑似泄露"而无法确认凭据是否仍然可用、归属于谁、该如何处置。

二、主要创新点

  1. 凭据对关联（组合风险分析）：识别"单条无法利用、成对出现才构成完整凭据"的组合

（如 AccessKey ID + Secret、OAuth Client ID + Client Secret、JWT + 签名密钥），

将组合风险升级为最高等级——这是多数同类工具不做、但真实安全价值极高的一层。

  1. 可解释概率评分 + 权重自适应：把"命中是否为真实凭据"建模为特征向量的概率，

每条判定都能解释"为什么"；并可从人工反馈样本中自动校准权重，实现"越用越准"。

  1. 误报反馈闭环：误报不是加白名单，而是作为训练样本重新调整判定边界，

形成"标注 → 校准 → 生效 → 抑制 → 复核"的完整闭环。

  1. 规则自动归纳：从已确认的泄露样本自动起草候选规则（公共前缀、长度区间、字符集、

熵区间 + 冲突检测），应对新平台格式变化。

  1. 容器镜像"删了不等于没有"检测：镜像分层存储 + 构建历史（ENV/ARG 残留）

是容易被忽略的高危泄露渠道。

一、问题定义与技术目标

云上凭据（AccessKey/SecretKey、API Token、数据库连接串、SSH 私钥、OAuth Client Secret 等）

是访问云上资产的"钥匙"。一旦泄露，攻击者可以合法身份访问资源，

绕过绝大多数传统安全防护手段。

本赛题要求解决的问题，本质上是三个工程难题的叠加：

难题具体表现本方案的对策
线索分散凭据散落在代码仓库、镜像层、发布包、Wiki、Paste、App 等十余类渠道15 个渠道适配器 + 插件化注册表
噪声极高关键词搜索命中大量示例值、变量引用、文档片段四层收敛过滤，逐层压缩误报
必须够快泄露窗口从数天压缩到分钟级才有实际价值增量游标 + 事件流订阅 + MTTD 度量

设计目标

  1. 准：宁可少报，不可误报。误报会让应急响应失去信任。
  2. 全：渠道覆盖面本身就是赛题评分项，也是真实检测能力的体现。
  3. 快：以分钟级发现延迟为目标，并把它变成可量化指标。
  4. 稳：单渠道失败不影响整体扫描；任何环节都不产生攻击性行为。

三、采集层：插件化渠道适配

3.1 扩展接口

class SourceAdapter(abc.ABC):
    meta: SourceMeta                      # 渠道元信息，供自动生成渠道清单

    @abc.abstractmethod
    def discover(self, cursor) -> Iterator[RawDoc]:
        """产出本轮的原始文档，cursor 用于增量续扫。"""

    def normalize(self, raw: RawDoc) -> Iterator[Document]:
        """默认实现：文本抽取；若为归档则自动展开成员。"""

    def next_cursor(self, raw: RawDoc) -> dict:
        """默认实现：记录最新 ID 与发布时间。"""

新增渠道 = 实现 discover 一个方法 + 一份 YAML 配置。

normalize 与 next_cursor 由基类提供，归档类渠道无需关心解包细节。

这正是赛题"平台可扩展性、新监控渠道的易扩展性"评分项的落地方式：

扩展成本是一个方法，而不是改一处调用链。

3.3 三个设计要点

① 容器镜像渠道：删了不等于没有

镜像采用分层存储。某一层里写入过密钥，即使后续层删除了该文件，

前面那层依然完整保留内容。同时镜像的 **config blob 中的 history 字段

会记录每层的构建命令**，ENV SECRET_KEY=...、ARG TOKEN=... 被完整保留。

因此本实现对镜像采集两类内容：

  • image_history：把 history 中各层 created_by 与 config.Env 拼成文本送检——命中率最高；
  • image_layer：逐层拉取 blob、gunzip、解 tar，对每个成员做文本抽取或字符串抽取。

② 移动端渠道：APK 本质是 zip

APK 直接解包后扫描 assets/、res/raw/、res/values/strings.xml、

AndroidManifest.xml，以及 classes.dex 中的可见字符串；

若本机存在 jadx，则进一步反编译 dex 得到可读源码，命中率显著提升。

小程序包（.wxapkg）按公开格式自行实现解包器：

读取 14 字节头部（0xBE 起始标记、索引长度、数据长度、0xED 结束标记），

解析索引区条目（nameLen / name / offset / size），

再按偏移从数据区取出各成员。加密版本会明确报错而非静默失败。

③ 时效性：订阅"刚刚发生"而不是"已经发生"

github 渠道的 recent 模式读取公共事件流，抓取刚刚推送的提交内容，

这是把 MTTD 做到分钟级的关键。相比之下，代码搜索 API 覆盖的是存量历史，

两者互补：search 保广度，recent 保时效。

3.4 合规与限速

  • 所有渠道通过 RateLimiter（滑动窗口）强制限速，参数写在渠道元信息里；
  • 令牌通过 TokenPool 轮换，遇 403/429 自动切下一个，避免单令牌被打满；
  • HttpClient 统一带退避重试与自定义 UA；
  • 不登录、不绕过风控、不访问非公开内容；未配置令牌的渠道直接跳过，

不会退化为主力爬虫。

四、解析层：让二进制内容也能被检测

4.1 文本抽取

输入 bytes
  ├─ looks_textual()？  → 按编码探测解码（UTF-8 / GB18030 / Big5 / Latin-1）
  └─ 二进制            → extract_strings()：抽取长度 ≥6 的可打印 ASCII 串

为什么二进制也要抽字符串：镜像层、.so、.dex、.class 中的凭据

绝大多数以明文可见字符串的形式存在。放弃二进制等于放弃了一半渠道。

4.2 归档解包与安全约束

支持 zip / jar / war / apk / whl / tar / tar.gz / tgz / gz / wxapkg。

5.1.1 结构化解析

对有语法的文件就用语法解析，而不是拿正则去猜。准确率显著更高，

且几乎不产生误报。覆盖五类结构：

结构解析对象关键处理
dotenv.env / 环境导出脚本变量名匹配凭据模式 + 值合法性校验
INI~/.aws/credentials / 部署配置段名（[default]/[credentials]）+ 键名双重确认
k8s Secretkind: Secret 清单data 字段 Base64解码后再判定
镜像构建Dockerfile / docker historyENV / ARG 行
PEM 私钥任意文件整块提取密钥内容

值合法性校验会排除：纯数字、单字符重复、布尔值、路径、环境变量引用、

localhost、常见非敏感取值（utf-8/debug/production 等）。

5.1.2 规则引擎

195 条 YAML 规则，覆盖 7 大类、59 种凭据类型。单条规则字段：

- id: aliyun-access-key-id
  name: 阿里云 AccessKey ID
  kind: 云访问密钥 ID
  severity: critical
  pattern: '(?<![A-Za-z0-9])(LTAI[A-Za-z0-9]{12,20})(?![A-Za-z0-9])'
  keywords: [aliyun, access_key, access_key_id]
  validator: aliyun
  description: 阿里云主账号或子账号 AccessKey ID。

三个值得说明的机制：

（1）secret_group：连接串必须取到口令，而不是用户名

mysql://app_rw:Pr0d_xxx@host/db 的正则第 1 个捕获组是用户名。

如果不显式指定，规则引擎会把用户名当成凭据上报——既报错对象，也无法验活。

因此连接串类规则统一标注 secret_group: 2。

（2）require_keywords：泛化规则的邻域约束

像"64 位十六进制"这种宽泛格式（linode-api-token、datadog-api-key），

在全量文本中会命中大量哈希值。这类规则要求关键词必须在**命中位置 ±240 字符

的邻域内共现**才算命中：

- id: datadog-api-key
  pattern: '(?<![A-Za-z0-9])([a-f0-9]{32})(?![A-Za-z0-9])'
  require_keywords: [datadog, dd_api_key, DD_API_KEY]

（3）私钥规则必须要求密钥体

只匹配 -----BEGIN RSA PRIVATE KEY----- 这一行会产生明显的系统性误报——

技术文档、教程、README 里经常成段引用这一行文字。

因此私钥规则改为"头部 + 至少两行、每行 ≥40 字符的 Base64 密钥体"：

-----BEGIN RSA PRIVATE KEY-----[\r\n]+(?:[A-Za-z0-9+/=]{40,}[\r\n]+){2,}

5.1.3 香农熵检测

规则库只能覆盖已知格式。对自研系统密钥、内部平台 token 这类

没有公开格式的凭据，靠熵值兜底：

$$H(X) = -\sum_{i=1}^{n} p(x_i) \log_2 p(x_i)$$

采纳条件：长度 20–128、熵 ≥ 4.5 bit/char、字符集 ≥ 2 类、

非纯数字/纯小写、通过占位符与噪声（哈希文件名、sha256: 前缀等）过滤。

环境引用os.environ[...] process.env.X
低信息量长度 <4、字符种类 ≤2、true/null/none

② 整段匹配占位符识别（is_placeholder_match）

与 ① 的区别：① 只看捕获组，② 看整段匹配。

因为 DSN 类规则的"示例特征"往往出现在用户名位置，

不在捕获组里——mysql://user:password@host/db 就是典型。

\buser(?:name)?\b\s*[:/]\s*\bpass(?:word|wd)?\b     → user:password@
<[A-Z_]{2,}>                                          → <YOUR_KEY>
\$\{[A-Z_]+\}                                          → ${ENV_VAR}
example\.(?:com|org|net)                               → example.com

第 3 层：上下文评分

规则与熵只看"字符串长什么样"。真正决定一条命中是不是真实泄露的，

是它出现在什么位置、旁边写了什么。本层把上下文证据折算为 0~1 的置信度：

证据权重
左侧存在敏感标识符（变量名 / 配置键）+0.30
紧邻赋值运算符+0.05
命中位置在敏感文件（.env / credentials / docker-compose 等）+0.25
命中结构化格式规则+0.15
邻近存在凭据类关键词+0.15
文档/示例路径（README / docs/ / tests/ / fixture）−0.25
疑似摘要/校验值上下文（sha256 / md5 / integrity）−0.35
邻近存在示例提示词−0.30
疑似环境变量引用而非明文−0.20

置信度合成：

confidence = 0.5 × 严重度权重 + 0.5 × 上下文分数
严重度权重：critical 1.0 / high 0.85 / medium 0.7 / low 0.5

按检测器设置不同阈值——这是关键的调参点：

检测器阈值理由
structured0.45结构化解析本身精确度极高，可以放宽
rule0.45格式规则已有强证据
entropy0.68熵检测天然噪声大，必须有强上下文才采纳

第 3.5 层：位置重叠合并

同一处内容可能被多个检测器命中。例如一段 PEM 私钥：

  • "私钥头"规则只匹配到 -----BEGIN RSA PRIVATE KEY-----（信息不全）；
  • 结构化解析拿到完整密钥块（信息完整）。

两者位置重叠，应当只保留信息更完整的那条。

因此合并逻辑不是"相同 span 去重"，而是重叠区间按检测器优先级合并：

if cand.span[0] < last.span[1]:        # 区间重叠
    if priority(cand) > priority(last): # 保留优先级更高的
        merged[-1] = cand
    continue

七、输出层

7.1 指纹去重

为什么去重能力直接决定成绩的可信度：

同一个密钥被 20 个仓库转载、被 3 个镜像层打包，

如果不去重就会虚报成 20+ 条"发现"，一旦评审抽查就站不住脚。

正确做法是"1 个凭据、N 个暴露位置"：

fingerprint = HMAC-SHA256(salt, secret)
  • 带盐，不可逆推明文；
  • 跨渠道、跨批次稳定，同一凭据必然聚合到同一 cluster；
  • 同文件内同一凭据只记一次；跨文件必须分别保留（这是曝光度的体现）。

7.2 跨渠道关联

if channel_count >= 2 or len(source_categories) >= 2:
    multi_channel = True
    severity = escalate(severity)          # 风险等级上调一级
    confidence += 0.10                     # 置信度提升

语义：凭据同时出现在代码仓库和容器镜像里，说明泄露面已经扩散，

攻击者更容易发现它，因此风险等级应当上调。

实现细节：渠道类别从 Document.metadata 逐层透传到 Finding.metadata。 若不透传，跨渠道判定会退化成"不同规则名也算跨渠道"，产生误判。

7.3 归属识别

赛题评审看"作品的应用价值"。一条"AKIA****f9Xz 泄露在某个仓库"，

和一条"某企业的云账号密钥泄露在 GitHub 仓库 X 的 .env，

可通过仓库 Security 页面联系"，实用价值完全不同。

线索抽取方式
平台与主体从 URL 提取仓库 owner/project
归档主体从 url#member 中取归档文件名（而非包内路径）
域名与组织域名后缀映射（.edu.cn→教育、.gov.cn→政府、.com→企业）
组织名称内置常见域名映射表，可扩充为配置文件
云厂商规则 ID 匹配 → 附上对应云厂商应急响应中心

输出负责任披露建议：不同平台给出不同的联系渠道

（GitHub 走 Security 页面、npm 走 package.json maintainers、

Paste 站点联系平台方删除内容等）。

7.4 时效性度量（MTTD）

MTTD = 发现时间 − 凭据首次公开时间

报告输出最小值 / 中位数 / 平均值 / 最大值与延迟分布图。

这把"发现够快"从形容词变成了可量化、可对比的数字。

八、数据安全设计

平台自身绝不能成为新的泄露源。为此在数据模型层做了强制约束：

措施实现

创新点 1：凭据对关联（组合风险分析）

为什么必要

绝大多数凭据扫描工具的输出是一条条孤立的字符串。但从攻击者视角看：

  • 单独一个 AWS Access Key ID 无法利用，必须配上 Secret 才能调用 API；
  • 单独一个 OAuth Client ID 只是公开标识，配上 Client Secret 才能冒充应用；
  • 单独一个 JWT 只是会话凭证，配上签名密钥就能伪造任意身份。

也就是说，两条中风险凭据同时出现，实际风险高于任意一条严重凭据单独出现。

这是 1 + 1 > 2 的组合风险，而现有工具（包括 gitleaks、trufflehog）普遍不做这层关联。

怎么实现

credwatch/correlation.py 定义了 9 类凭据对（云厂商 AK/SK、OAuth Client、JWT+签名密钥、

加密私钥+口令、支付宝/微信支付商户对等），在两个范围做关联：

范围含义可信度
document同一文件内成对出现高（几乎必然同一次硬编码）
origin同一仓库/工程目录/镜像内成对出现中（跨文件引用同样可用）

命中后：整组成员风险等级升级为 critical，置信度上调，并在报告中给出

"该组合可直接被攻击者利用"的具体危害说明与处置优先级。

怎么验证

真实渠道实测：三轮独立扫描中，数字资产私钥（比特币 WIF、以太坊私钥）

与 OpenSSH 私钥被持续识别并升级为 critical（第三轮 46 个，见《测试报告》8.8）。

单元测试覆盖了"同文件配对""跨文件配对""不同仓库不误关联""单条不误报"四种边界。

创新点 2：可解释概率评分 + 权重自适应

为什么必要

传统扫描器给一个"分数"，但说不清这个分数怎么来的。评审问"这条为什么判为真"，

只能答"分数够了"。这既不利于答辩，也不利于调参——不知道哪个信号起了作用，

就只能靠拍脑袋改阈值。

怎么实现

credwatch/detectors/scoring.py 把判定改造成特征向量 + 逻辑回归：

  1. 19 维特征：左侧是否有敏感变量名、是否在 .env 里、值是否带已知前缀、

熵是否够高、是否出现在文档路径里、邻近是否有哈希/校验值等；

  1. 概率输出：p = sigmoid(w·x + b)，输出直接读作"这是真实凭据的概率"；
  2. 可解释：返回每个特征的贡献量 特征值 × 权重，按影响力排序；
  3. 权重可校准：初始权重是安全工程师的专家先验，有了人工标注后，

用带 L2 正则 + 先验锚定的逻辑回归重新拟合。

"先验锚定"是防止小样本跑偏的关键——样本越少，先验的话语权越大。

怎么验证

演示脚本 scripts/demo_feedback_loop.py 在 15 条标注样本上把准确率从

0.533 提升到 0.933，精确率从 0.533 提升到 1.000。

报告中的每条发现都附有"判定依据"，答辩时可直接逐条讲解。

创新点 3：误报反馈闭环

为什么必要

任何扫描器都会误报。区别在于：误报之后发生了什么。

  • 多数工具：用户只能把误报项从列表里删掉，下次照旧误报；
  • 本系统：把误报标记为训练样本 → 重新校准评分权重 → 改变判定边界本身。

前者是"打补丁"，后者是"真的变聪明"。

完整闭环

标注（确认 / 误报，特征向量随标注入库）
  → 校准（逻辑回归 + 先验锚定，产出新权重）
  → 生效（下次扫描自动加载）
  → 抑制（已确认的误报指纹不再重复上报）
  → 复核（重扫确认修复结果）

对应的命令：credwatch feedback、credwatch calibrate、credwatch verify。

创新点 4：规则自动归纳

为什么必要

规则库最大的敌人是格式变化——新平台上线、老平台改 token 格式，手写规则永远追不上。

怎么实现

credwatch/rule_induction.py 从一批已确认的泄露样本自动归纳候选规则：

  1. 提取公共前缀（sk-、ghp_、LTAI）；
  2. 统计长度区间（样本足够时收紧到固定长度）；
  3. 判定字符集（全大写+数字 / 字母数字 / 含符号）；
  4. 计算熵区间（剔除纯数字串）；
  5. 生成候选 YAML，并做与已有规则的冲突检测。

关键是"候选 + 人工审核"的定位：归纳是启发式的，可能过拟合少数样本，

它负责把写规则从"完全手工"变成"机器起草 + 人工审核"，而不是替人做决定。

怎么验证

python -m credwatch induce-rule --samples "demo-xxx,demo-yyy" 现场生成一条能命中

全部样本的候选规则，并自动报告与现有规则的重叠。

第 1 轮离线合成语料 25 份30 个唯一凭据，反例零命中合成语料太"干净"，掩盖了真实噪声

由此落地了三项机制，并各自固化为单元测试：

  1. 熵检测佐证门控：无敏感标识符/已知前缀/敏感文件佐证的熵命中一律拦截；
  2. 规则收紧：docker-history-secret 移除裸 -p，并排除以 / 开头的路径；
  3. 命中风暴抑制：同一文档内同一规则最多上报 50 条（按置信度保留），超出合并计数并标注。

这轮迭代的价值不在"修了三个 bug"，而在证明这套系统具备"在真实数据上持续收敛"的能力——

离线指标好看不算数，真实数据上能站住才算数。

创新点 6：渠道脚手架（可扩展性现场证明）

赛题评分项"平台可扩展性、新监控渠道的易扩展性"。光说架构灵活没有用，

要让评审当场看到。

python -m credwatch new-source 某平台 --label "某平台"

30 秒内生成：渠道实现骨架（只需填 discover() 一个方法）、自动注册到渠道注册表、

自动追加到配置文件。答辩时可现场演示"接入一个新渠道"。

架构上，新增渠道 = 继承 SourceAdapter 实现 discover()，

normalize()（含归档/镜像/小程序解包）与 next_cursor()（增量游标）由基类提供默认实现。

创新点 7：容器镜像"删了不等于没有"检测

这是渠道覆盖上容易被忽略、却危害最大的一类：

  1. 镜像分层存储，某层写入过密钥，即使后面的层删掉文件，前面的层依然保留完整内容；
  2. 镜像 config blob 的 history 字段完整记录每层的构建命令，

ENV SECRET_KEY=...、ARG TOKEN=... 被原样保留。

因此本系统对镜像采集两类内容：image_history（构建历史，命中率最高）与

image_layer（逐层解包后的文件系统）。同时给出"构建期改用 BuildKit secret"的根因修复建议。

创新点 8：只读活性验证（自实现云签名）

把"疑似泄露"升级为"已确认可用"，是应急响应价值的关键。本系统实现了 16 个

只读验证器，其中 **AWS SigV4、阿里云 HMAC-SHA1、腾讯云 TC3-HMAC-SHA256 三种签名算法

均依据官方公开文档自行实现**，未使用任何云 SDK。

安全护栏（代码级强制）：默认关闭、全局限速、只读接口白名单；

没有统一只读入口的平台（华为云、Google API Key）明确返回"无法判定"，

不做猜测性判定。

创新点 9：可复现性能基准 + 规则库自检

  • 性能基准 credwatch bench：固定随机种子生成语料，输出吞吐量、阶段耗时、

规则热点、峰值内存，任何人可复现出同样的数字。

  • 规则库自检 credwatch lint-rules：校验正则编译、ID 重复、secret_group 越界、

验证器存在性、格式特异性，把"规则文件是数据，数据也要校验"落到实处。

五、为什么"发现凭据数量"能站得住

赛题评分项里有"发现凭据的数量"。数量本身不是目的，真实的数量才是。

  1. 指纹去重：同一密钥被 8 个文件转载，算作"1 个凭据、8 个暴露位置"，

而不是虚报成 8 个凭据——评审抽查不会翻车；

  1. 占位符过滤：your_key_here、<TOKEN>、示例 DSN 一律不计入；
  2. 只读验活：能确认"仍然有效"的凭据单独标注，与"疑似"区分；
  3. 降级线索与告警分级：低级别的上下文提示不算入"发现凭据"的口径。

这样报出的数量，是经得起逐条核查的数量。

六、路线图：在公开基准上量化对表（下一迭代）

针对 2.1 节"公开基准量化"差距，明确的评测计划：

  1. 数据集：SecretBench（15,084 条人工标注真凭据 / 818 仓库）为主，

CredData（19.4M 行）为辅；

  1. 口径：与 CredData 基准表同口径统计 TP/FP/TN/FN → precision / recall / F1，

并按凭据类型分桶报告；

  1. 对比对象：CredSweeper（F1 0.8586）与 gitleaks（F1 0.334）的已发表数字；
  2. 预期：可解释评分路线的 precision 应显著高于纯正则工具（占位符过滤+上下文

确认是主要贡献），recall 的短板预计在长尾平台格式（规则数差距所在）——

这将用规则自动归纳迭代补齐；

  1. 产出：评测脚本与结果并入《测试报告》，作为答辩的量化对比证据。

七、诚实的局限

不回避短板，评审问起来也答得清：

  1. doc_share / search_engine 依赖第三方搜索接口稳定性，默认关闭、可配置；
  2. 华为云 / Google API Key 无法自动验活，明确返回"待人工复核"；
  3. 加密的 wxapkg 包不支持，解析器会明确报错而非静默失败；
  4. 规则库规模不及 TruffleHog（195 vs 800+）——公开基准评测（第六节）之前，

不做检测率的横向量化断言；

  1. ML 误报过滤未采用（CredSweeper 路线）——当前用可解释概率评分替代，

若基准评测显示 recall 短板，轻量 RNN 是现成的补强路径；

  1. 基准中的"其他"耗时偏高，说明 I/O 与去重环节还有优化空间。

二、活性验证的安全护栏

class ValidationGuard:
    def allow(self) -> bool:
