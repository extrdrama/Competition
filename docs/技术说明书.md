# 凭迹 CredWatch · 技术说明书

**面向赛题**："华为杯"第五届中国研究生网络安全创新大赛 揭榜挑战赛 题目3
《云上凭据泄露的自动化检测》

**版本**：1.0.0

---

## 一、问题定义与技术目标

云上凭据（AccessKey/SecretKey、API Token、数据库连接串、SSH 私钥、OAuth Client Secret 等）
是访问云上资产的"钥匙"。一旦泄露，攻击者可以**合法身份**访问资源，
绕过绝大多数传统安全防护手段。

本赛题要求解决的问题，本质上是**三个工程难题的叠加**：

| 难题 | 具体表现 | 本方案的对策 |
| --- | --- | --- |
| **线索分散** | 凭据散落在代码仓库、镜像层、发布包、Wiki、Paste、App 等十余类渠道 | 15 个渠道适配器 + 插件化注册表 |
| **噪声极高** | 关键词搜索命中大量示例值、变量引用、文档片段 | 四层收敛过滤，逐层压缩误报 |
| **必须够快** | 泄露窗口从数天压缩到分钟级才有实际价值 | 增量游标 + 事件流订阅 + MTTD 度量 |

### 设计目标

1. **准**：宁可少报，不可误报。误报会让应急响应失去信任。
2. **全**：渠道覆盖面本身就是赛题评分项，也是真实检测能力的体现。
3. **快**：以分钟级发现延迟为目标，并把它变成可量化指标。
4. **稳**：单渠道失败不影响整体扫描；任何环节都不产生攻击性行为。

## 二、总体架构

系统分为五层，层间通过明确的中间数据结构解耦：

```
┌──────────────────────────────────────────────────────────────┐
│ 采集层 Source Adapter（15 个渠道，插件化注册）                   │
│  代码托管 / 容器镜像 / 包仓库 / Paste / Wiki / 社媒 / App / 本地  │
└──────────────────────────┬───────────────────────────────────┘
                           │ RawDoc{source, url, content, published_at}
┌──────────────────────────▼───────────────────────────────────┐
│ 解析层 Parser                                                 │
│  文本抽取（编码探测、二进制字符串抽取）                            │
│  归档解包（zip/tar/gz/apk/wxapkg）+ 镜像层解包（含 zip bomb 防护）│
└──────────────────────────┬───────────────────────────────────┘
                           │ Document{doc_id, text, path_hint, ...}
┌──────────────────────────▼───────────────────────────────────┐
│ 检测层 Detection Pipeline（四层收敛）                          │
│  ① 结构化解析 / 规则引擎 / 香农熵 → 候选                        │
│  ② 占位符过滤 + 关键词邻域校验                                  │
│  ③ 上下文评分 → 置信度阈值截断                                 │
└──────────────────────────┬───────────────────────────────────┘
                           │ Finding{fingerprint, masked, evidence}
┌──────────────────────────▼───────────────────────────────────┐
│ 验证层 Validator（只读活性验证，默认关闭）                       │
│  AWS STS / 阿里云 STS / 腾讯云 STS / GitHub / GitLab / Slack ...│
└──────────────────────────┬───────────────────────────────────┘
                           │ validated: True / False / None
┌──────────────────────────▼───────────────────────────────────┐
│ 输出层 Dedup → Attribution → Storage → Report                │
│  指纹去重 / 跨渠道关联 / 归属识别 / 披露建议 / MTTD / 看板        │
└──────────────────────────────────────────────────────────────┘
```

### 关键中间数据结构

| 结构 | 作用 | 关键字段 |
| --- | --- | --- |
| `RawDoc` | 渠道采集的原始内容 | `source` `url` `content` `published_at` |
| `Document` | 归一化后的待检测文本 | `text` `path_hint` `discovered_at` |
| `Candidate` | 检测器产出的候选命中 | `secret` `span` `line_no` `detector` |
| `Finding` | 单处暴露记录 | `fingerprint` `masked` `evidence` `confidence` |
| `CredentialCluster` | 同一凭据的全部暴露证据 | `exposures` `sources` `mtd_hours` |

## 三、采集层：插件化渠道适配

### 3.1 扩展接口

```python
class SourceAdapter(abc.ABC):
    meta: SourceMeta                      # 渠道元信息，供自动生成渠道清单

    @abc.abstractmethod
    def discover(self, cursor) -> Iterator[RawDoc]:
        """产出本轮的原始文档，cursor 用于增量续扫。"""

    def normalize(self, raw: RawDoc) -> Iterator[Document]:
        """默认实现：文本抽取；若为归档则自动展开成员。"""

    def next_cursor(self, raw: RawDoc) -> dict:
        """默认实现：记录最新 ID 与发布时间。"""
```

**新增渠道 = 实现 `discover` 一个方法 + 一份 YAML 配置**。
`normalize` 与 `next_cursor` 由基类提供，归档类渠道无需关心解包细节。

这正是赛题"平台可扩展性、新监控渠道的易扩展性"评分项的落地方式：
扩展成本是**一个方法**，而不是改一处调用链。

### 3.2 渠道清单（15 个 / 10 类）

| 类别 | 渠道 | 采集方式 |
| --- | --- | --- |
| 代码托管平台 | `github` | 代码搜索 API + 仓库树遍历 + **公共事件流** + 公开 Gist |
| | `gitee` | 开放 API 代码搜索 |
| | `gitlab` | Blob 搜索 API（支持自建实例） |
| 容器镜像 | `container_registry` | Registry V2 API：配置 blob（构建历史）+ 逐层文件系统 |
| 包仓库 | `npm_registry` | npm registry 搜索 + tarball 下载解包 |
| | `pypi_registry` | PyPI 官方"最近更新"RSS + sdist 下载解包 |
| 公开分享 | `paste_site` | Pastebin / Ghostbin / Hastebin 公开列表 + Raw 页 |
| Wiki 与知识库 | `mediawiki` | 标准 `api.php` 搜索 + 页面正文 |
| | `confluence` | REST `/rest/api/search` |
| 内容共享 | `doc_share` | 可配置端点模板（掘金等） |
| 社交媒体 | `weibo` | 开放平台官方 API |
| 搜索引擎 | `search_engine` | `site:` 语法定向补充（需自备端点） |
| App 与小程序 | `mobile_app` | APK/AAB 解包 + dex 字符串抽取 + 可选 jadx 反编译 |
| | `mini_program` | wxapkg 格式解包 |
| 本地与企业内网 | `local_dir` | 递归目录扫描 + 内容哈希增量 |

### 3.3 三个设计要点

**① 容器镜像渠道：删了不等于没有**

镜像采用**分层存储**。某一层里写入过密钥，即使后续层删除了该文件，
前面那层依然完整保留内容。同时镜像的 **config blob 中的 `history` 字段
会记录每层的构建命令**，`ENV SECRET_KEY=...`、`ARG TOKEN=...` 被完整保留。

因此本实现对镜像采集两类内容：

- `image_history`：把 `history` 中各层 `created_by` 与 `config.Env` 拼成文本送检——命中率最高；
- `image_layer`：逐层拉取 blob、gunzip、解 tar，对每个成员做文本抽取或字符串抽取。

**② 移动端渠道：APK 本质是 zip**

APK 直接解包后扫描 `assets/`、`res/raw/`、`res/values/strings.xml`、
`AndroidManifest.xml`，以及 `classes.dex` 中的可见字符串；
若本机存在 `jadx`，则进一步反编译 dex 得到可读源码，命中率显著提升。

小程序包（`.wxapkg`）按公开格式自行实现解包器：
读取 14 字节头部（`0xBE` 起始标记、索引长度、数据长度、`0xED` 结束标记），
解析索引区条目（`nameLen` / `name` / `offset` / `size`），
再按偏移从数据区取出各成员。加密版本会明确报错而非静默失败。

**③ 时效性：订阅"刚刚发生"而不是"已经发生"**

`github` 渠道的 `recent` 模式读取公共事件流，抓取**刚刚推送**的提交内容，
这是把 MTTD 做到分钟级的关键。相比之下，代码搜索 API 覆盖的是存量历史，
两者互补：`search` 保广度，`recent` 保时效。

### 3.4 合规与限速

- 所有渠道通过 `RateLimiter`（滑动窗口）强制限速，参数写在渠道元信息里；
- 令牌通过 `TokenPool` 轮换，遇 403/429 自动切下一个，避免单令牌被打满；
- `HttpClient` 统一带退避重试与自定义 UA；
- **不登录、不绕过风控、不访问非公开内容**；未配置令牌的渠道直接跳过，
  不会退化为主力爬虫。

## 四、解析层：让二进制内容也能被检测

### 4.1 文本抽取

```
输入 bytes
  ├─ looks_textual()？  → 按编码探测解码（UTF-8 / GB18030 / Big5 / Latin-1）
  └─ 二进制            → extract_strings()：抽取长度 ≥6 的可打印 ASCII 串
```

为什么二进制也要抽字符串：镜像层、`.so`、`.dex`、`.class` 中的凭据
**绝大多数以明文可见字符串的形式存在**。放弃二进制等于放弃了一半渠道。

### 4.2 归档解包与安全约束

支持 zip / jar / war / apk / whl / tar / tar.gz / tgz / gz / wxapkg。

安全约束（防 zip bomb）：

| 约束 | 阈值 |
| --- | --- |
| 最大条目数 | 20,000 |
| 单文件解包上限 | 8 MB |
| 总解包上限 | 200 MB |
| 最大压缩比 | 200:1 |

超限即抛错并跳过，绝不因一个恶意归档拖垮整个扫描任务。

## 五、检测层：四层收敛

这是系统的核心。以下逐层说明。

### 第 1 层：多引擎候选生成

三个检测器并行工作，各自覆盖不同场景：

| 检测器 | 适用场景 | 优先级 |
| --- | --- | --- |
| **结构化解析** `structured` | 有语法的配置文件 | 3（最高） |
| **规则引擎** `rule` | 已知格式的凭据 | 2 |
| **香农熵** `entropy` | 未知格式的自研系统密钥 | 1 |

#### 5.1.1 结构化解析

对**有语法的文件**就用语法解析，而不是拿正则去猜。准确率显著更高，
且几乎不产生误报。覆盖五类结构：

| 结构 | 解析对象 | 关键处理 |
| --- | --- | --- |
| dotenv | `.env` / 环境导出脚本 | 变量名匹配凭据模式 + 值合法性校验 |
| INI | `~/.aws/credentials` / 部署配置 | 段名（`[default]`/`[credentials]`）+ 键名双重确认 |
| k8s Secret | `kind: Secret` 清单 | `data` 字段 Base64**解码后**再判定 |
| 镜像构建 | Dockerfile / `docker history` | `ENV` / `ARG` 行 |
| PEM 私钥 | 任意文件 | 整块提取密钥内容 |

值合法性校验会排除：纯数字、单字符重复、布尔值、路径、环境变量引用、
localhost、常见非敏感取值（`utf-8`/`debug`/`production` 等）。

#### 5.1.2 规则引擎

195 条 YAML 规则，覆盖 7 大类、59 种凭据类型。单条规则字段：

```yaml
- id: aliyun-access-key-id
  name: 阿里云 AccessKey ID
  kind: 云访问密钥 ID
  severity: critical
  pattern: '(?<![A-Za-z0-9])(LTAI[A-Za-z0-9]{12,20})(?![A-Za-z0-9])'
  keywords: [aliyun, access_key, access_key_id]
  validator: aliyun
  description: 阿里云主账号或子账号 AccessKey ID。
```

三个值得说明的机制：

**（1）`secret_group`：连接串必须取到口令，而不是用户名**

`mysql://app_rw:Pr0d_xxx@host/db` 的正则第 1 个捕获组是用户名。
如果不显式指定，规则引擎会把用户名当成凭据上报——既报错对象，也无法验活。
因此连接串类规则统一标注 `secret_group: 2`。

**（2）`require_keywords`：泛化规则的邻域约束**

像"64 位十六进制"这种宽泛格式（`linode-api-token`、`datadog-api-key`），
在全量文本中会命中大量哈希值。这类规则要求关键词必须在**命中位置 ±240 字符
的邻域内共现**才算命中：

```yaml
- id: datadog-api-key
  pattern: '(?<![A-Za-z0-9])([a-f0-9]{32})(?![A-Za-z0-9])'
  require_keywords: [datadog, dd_api_key, DD_API_KEY]
```

**（3）私钥规则必须要求密钥体**

只匹配 `-----BEGIN RSA PRIVATE KEY-----` 这一行会产生**明显的系统性误报**——
技术文档、教程、README 里经常成段引用这一行文字。
因此私钥规则改为"头部 + 至少两行、每行 ≥40 字符的 Base64 密钥体"：

```
-----BEGIN RSA PRIVATE KEY-----[\r\n]+(?:[A-Za-z0-9+/=]{40,}[\r\n]+){2,}
```

#### 5.1.3 香农熵检测

规则库只能覆盖**已知格式**。对自研系统密钥、内部平台 token 这类
没有公开格式的凭据，靠熵值兜底：

$$H(X) = -\sum_{i=1}^{n} p(x_i) \log_2 p(x_i)$$

采纳条件：长度 20–128、熵 ≥ 4.5 bit/char、字符集 ≥ 2 类、
非纯数字/纯小写、通过占位符与噪声（哈希文件名、`sha256:` 前缀等）过滤。

### 第 2 层：占位符与关键词过滤

这是**凭据扫描类工具误报的最大来源**，必须单独成层。两道过滤：

**① 值级占位符识别**（`is_placeholder`）

| 类型 | 示例 |
| --- | --- |
| 掩码 | `***` `xxx` `####` |
| 前缀词 | `your_` `my_` `test_` `example_` `dummy_` `fake_` |
| 占位词 | `placeholder` `changeme` `replace_me` `todo` |
| 尖括号/变量 | `<TOKEN>` `${ENV_VAR}` `[KEY]` |
| 环境引用 | `os.environ[...]` `process.env.X` |
| 低信息量 | 长度 <4、字符种类 ≤2、`true`/`null`/`none` |

**② 整段匹配占位符识别**（`is_placeholder_match`）

与 ① 的区别：① 只看捕获组，② 看整段匹配。
因为 DSN 类规则的"示例特征"往往出现在**用户名位置**，
不在捕获组里——`mysql://user:password@host/db` 就是典型。

```
\buser(?:name)?\b\s*[:/]\s*\bpass(?:word|wd)?\b     → user:password@
<[A-Z_]{2,}>                                          → <YOUR_KEY>
\$\{[A-Z_]+\}                                          → ${ENV_VAR}
example\.(?:com|org|net)                               → example.com
```

### 第 3 层：上下文评分

规则与熵只看"字符串长什么样"。真正决定一条命中是不是**真实泄露**的，
是它出现在什么位置、旁边写了什么。本层把上下文证据折算为 0~1 的置信度：

| 证据 | 权重 |
| --- | --- |
| 左侧存在敏感标识符（变量名 / 配置键） | +0.30 |
| 紧邻赋值运算符 | +0.05 |
| 命中位置在敏感文件（`.env` / `credentials` / `docker-compose` 等） | +0.25 |
| 命中结构化格式规则 | +0.15 |
| 邻近存在凭据类关键词 | +0.15 |
| **文档/示例路径**（`README` / `docs/` / `tests/` / `fixture`） | **−0.25** |
| 疑似摘要/校验值上下文（`sha256` / `md5` / `integrity`） | **−0.35** |
| 邻近存在示例提示词 | **−0.30** |
| 疑似环境变量引用而非明文 | **−0.20** |

**置信度合成**：

```
confidence = 0.5 × 严重度权重 + 0.5 × 上下文分数
严重度权重：critical 1.0 / high 0.85 / medium 0.7 / low 0.5
```

**按检测器设置不同阈值**——这是关键的调参点：

| 检测器 | 阈值 | 理由 |
| --- | --- | --- |
| `structured` | 0.45 | 结构化解析本身精确度极高，可以放宽 |
| `rule` | 0.45 | 格式规则已有强证据 |
| `entropy` | **0.68** | 熵检测天然噪声大，必须有强上下文才采纳 |

### 第 3.5 层：位置重叠合并

同一处内容可能被多个检测器命中。例如一段 PEM 私钥：

- "私钥头"规则只匹配到 `-----BEGIN RSA PRIVATE KEY-----`（信息不全）；
- 结构化解析拿到完整密钥块（信息完整）。

两者**位置重叠**，应当只保留信息更完整的那条。
因此合并逻辑不是"相同 span 去重"，而是**重叠区间按检测器优先级合并**：

```python
if cand.span[0] < last.span[1]:        # 区间重叠
    if priority(cand) > priority(last): # 保留优先级更高的
        merged[-1] = cand
    continue
```

## 六、验证层：把"疑似"变成"已确认"

### 6.1 为什么必须做

一个"已确认有效"的 AK 与一个"疑似泄露的字符串"，
在应急响应中的处置优先级完全不同。同时，过滤掉已吊销的凭据，
能让"发现凭据数量"这一指标反映真实风险规模。

### 6.2 16 个只读验证器

验证器的选取标准：**目标平台必须提供"读取自身身份/权限"的只读端点**。
凡是需要发送消息、创建资源、产生费用的接口一律不用。

| 验证器 | 调用接口 | 返回信息 |
| --- | --- | --- |
| `aws` | `sts:GetCallerIdentity`（SigV4 自实现签名） | 账号 ID、ARN |
| `aliyun` | `sts:GetCallerIdentity`（HMAC-SHA1 签名） | 账号 ID、ARN |
| `tencent` | `sts:GetCallerIdentity`（TC3-HMAC-SHA256 签名） | 账号 ID、ARN |
| `github` | `GET /user` | 归属账号、令牌权限范围 |
| `gitlab` | `GET /api/v4/user` | 归属账号 |
| `gitee` | `GET /api/v5/user` | 归属账号 |
| `slack` | `POST auth.test` | 团队、用户 |
| `openai` | `GET /v1/models` | 可用模型数 |
| `anthropic` | `GET /v1/models` | 有效性 |
| `stripe` | `GET /v1/balance` | 环境（生产/测试） |
| `sendgrid` | `GET /v3/scopes` | 权限范围 |
| `dockerhub` | `POST /v2/users/login` | 账号 |
| `twilio` | `GET /Accounts/{sid}.json` | 账号 |
| `huawei` / `google_api_key` | 不发起请求 | 明确标记"无法判定" |

> **诚实标注**：华为云与 Google API Key 缺少统一的匿名只读验证入口。
> 与其编造一个可能误判的请求，不如明确返回"无法判定，建议人工复核"。

### 6.3 三重安全护栏（代码强制）

```python
class ValidationGuard:
    def allow(self) -> bool:
        if not self.enabled:          # ① 默认关闭，必须显式开启
            return False
        with self._lock:              # ② 全局限速（默认 20 次/分钟）
            ...
```

3. **白名单接口**：验证器注册表是封闭的，只有注册在册的只读接口可被调用，
   框架层面不提供任何列举资源、读写数据的能力。

## 七、输出层

### 7.1 指纹去重

**为什么去重能力直接决定成绩的可信度**：
同一个密钥被 20 个仓库转载、被 3 个镜像层打包，
如果不去重就会虚报成 20+ 条"发现"，一旦评审抽查就站不住脚。

正确做法是"**1 个凭据、N 个暴露位置**"：

```
fingerprint = HMAC-SHA256(salt, secret)
```

- 带盐，不可逆推明文；
- 跨渠道、跨批次稳定，同一凭据必然聚合到同一 cluster；
- 同文件内同一凭据只记一次；**跨文件必须分别保留**（这是曝光度的体现）。

### 7.2 跨渠道关联

```
if channel_count >= 2 or len(source_categories) >= 2:
    multi_channel = True
    severity = escalate(severity)          # 风险等级上调一级
    confidence += 0.10                     # 置信度提升
```

语义：凭据同时出现在代码仓库和容器镜像里，说明泄露面已经扩散，
攻击者更容易发现它，因此风险等级应当上调。

> 实现细节：渠道类别从 `Document.metadata` 逐层透传到 `Finding.metadata`。
> 若不透传，跨渠道判定会退化成"不同规则名也算跨渠道"，产生误判。

### 7.3 归属识别

赛题评审看"作品的应用价值"。一条"`AKIA****f9Xz` 泄露在某个仓库"，
和一条"某企业的云账号密钥泄露在 GitHub 仓库 X 的 `.env`，
可通过仓库 Security 页面联系"，实用价值完全不同。

| 线索 | 抽取方式 |
| --- | --- |
| 平台与主体 | 从 URL 提取仓库 `owner/project` |
| 归档主体 | 从 `url#member` 中取归档文件名（而非包内路径） |
| 域名与组织 | 域名后缀映射（`.edu.cn`→教育、`.gov.cn`→政府、`.com`→企业） |
| 组织名称 | 内置常见域名映射表，可扩充为配置文件 |
| 云厂商 | 规则 ID 匹配 → 附上对应云厂商应急响应中心 |

输出**负责任披露建议**：不同平台给出不同的联系渠道
（GitHub 走 Security 页面、npm 走 package.json maintainers、
Paste 站点联系平台方删除内容等）。

### 7.4 时效性度量（MTTD）

```
MTTD = 发现时间 − 凭据首次公开时间
```

报告输出最小值 / 中位数 / 平均值 / 最大值与延迟分布图。
这把"发现够快"从形容词变成了可量化、可对比的数字。

## 八、数据安全设计

**平台自身绝不能成为新的泄露源**。为此在数据模型层做了强制约束：

| 措施 | 实现 |
| --- | --- |
| 明文不落盘 | `Finding.to_record()` 主动 `pop("raw")`，明文只存在于内存 |
| 掩码固定长度 | 中间固定 4 个星号，避免凭据真实长度被反推 |
| 私钥特殊处理 | 只保留头部标识与字节数，不保留任何密钥体 |
| 指纹带盐 | HMAC-SHA256，盐值由 `CREDWATCH_HMAC_SALT` 配置 |
| 报告脱敏 | 命中片段中的明文在 `snippet_of()` 中被替换为掩码 |

单元测试 `test_no_plaintext_in_json_output` 会对整份 JSON 报告做明文断言检查，
防止后续改动破坏这条底线。

## 十、局限与后续工作

诚实说明当前边界：

1. **`doc_share` / `search_engine` 渠道依赖外部接口稳定性。**
   第三方搜索接口随时可能调整，因此设计为可配置端点、默认关闭。
2. **华为云与 Google API Key 无法自动验活**，已明确标注为"待人工复核"，
   不做猜测性判定。
3. **加密的 wxapkg 包不支持**，解析器会明确报错而非静默失败。
4. **规则库仍需持续扩充。** 195 条规则覆盖主流平台，
   但新平台、新格式需要持续跟进；`secret_group` 与 `require_keywords`
   机制已为后续扩充留好接口。
5. **后续方向**：引入规则自动生成（从历史真阳性反推正则）、
   基于行为基线的异常检测、与 SIEM 的告警联动。
