# 凭迹 CredWatch · 答辩演示脚本（20 分钟）

决赛评审流程：现场答辩及作品演示，含 PPT 陈述、系统演示、测试与专家提问，
并现场检查源代码。本脚本按 **20 分钟** 编排，标注了每个环节的时长与"此刻屏幕上该出现什么"。

> 演示原则：**能现场跑的不讲 PPT，能现场改代码的不放截图**。
> 评审最反感"演示视频 + 背诵稿"。下面三个现场演示环节是本脚本的灵魂。

---

## 时间轴总览

| 阶段 | 时长 | 内容 |
| --- | --- | --- |
| 1. 开场定位 | 2 min | 我们解决什么问题，和通用工具的区别 |
| 2. 架构速览 | 3 min | 五层架构 + 四层收敛 + 15 渠道 + 178 规则 |
| 3. **现场演示①：离线扫描** | 4 min | `demo` 命令，讲收敛漏斗与误报控制 |
| 4. **现场演示②：三个创新点** | 5 min | 凭据对关联、可解释评分、反馈闭环 |

| 6. 性能与合规 | 2 min | 基准数字 + 合规红线 |
| 7. 收尾 + 答疑预案 | 1 min | 引导提问 + 备好答案 |

---

## 阶段 1：开场定位（2 分钟）

**讲什么**：凭据泄露是"用合法身份干非法的事"，绕过传统防护；发现窗口行业现状是
数天到数月。我们的目标是把窗口压到分钟级，且全程防御性。

**屏幕**：PPT 第一页——"云上凭据泄露的自动化检测" + 三个设计底线
（不做攻击 / 不成为新泄露源 / 不给第三方造成压力）。

**要点一句话**：`gitleaks 回答"这个仓库有没有密钥"，我们回答"全网公开渠道上
谁的凭据在泄露、多久了、怎么处置"`。

---

## 阶段 2：架构速览（3 分钟）

**屏幕**：架构图（采集 → 解析 → 检测 → 验证 → 输出五层）。

**逐层一句**：
- 采集：15 个渠道、10 个类别，插件化注册；
- 解析：文本抽取 + 归档/镜像层/wxapkg 解包（带 zip bomb 防护）；
- 检测：四层收敛（格式命中 → 占位符过滤 → 概率评分 → 活性验证）；
- 验证：16 个只读验证器，云签名自实现；
- 输出：指纹去重 + 凭据对关联 + 归属 + 处置建议 + MTTD。

**要点**：强调"扩展一个渠道 = 实现一个方法"，为阶段 5 埋钩子。

---

## 阶段 3：现场演示① 离线扫描（4 分钟）

**敲**：

```bash
python -m credwatch demo
```

**屏幕上会出现**：扫描概览、收敛漏斗、高优先级发现、组合风险表、渠道执行情况、报告路径。

**逐项讲**：

1. 收敛漏斗：`163 条格式命中 → 54 条上下文确认 → 29 个唯一凭据`——三层各自过滤了多少噪声；
2. 误报控制：点开报告，指出 `README.md` 里塞满了 `your_key_here`、`<TOKEN>`、
   `mysql://user:password@host/db`、单独一行私钥头，**该文件零命中**；
3. 脱敏：所有凭据只有掩码（`AKIA****f9Xz`）+ 指纹，明文不落盘。

**要点**：`29 个唯一凭据、51 个暴露位置`——去重后是 29 而不是 51，
因为同一个口令出现在 8 个文件里算"1 个凭据、8 处暴露"。评审抽查不翻车。

---

## 阶段 4：现场演示② 三个创新点（5 分钟）

### 4a. 凭据对关联（组合风险）

**讲**：单条 AK 无法利用，配上 SK 才是完整凭据。现有工具不做这层关联。

**屏幕**：报告第六节"组合风险：凭据对关联"——4 处密钥对被识别、升级 critical、
给出危害说明。

### 4b. 可解释评分

**讲**：每条判定都能解释"为什么"。点开报告里任意一条发现，读"判定依据"那一行：
`+2.20 左侧存在敏感变量名；+2.60 值具有已知前缀；−2.20 邻近示例提示词`。

**补一句**：这不是写死的 if-else，是特征向量 × 权重的概率模型。

### 4c. 误报反馈闭环

**敲**（先确保跑过 `demo`）：

```bash
python scripts/demo_feedback_loop.py --dry-run
```

**屏幕**：标注 15 条样本 → 校准后准确率 **0.533 → 0.933**、精确率 **→ 1.000**。
讲清楚：误报不是加白名单，是真的改变了判定边界。

**要点**：三个创新点都对应"别人没有做 + 确实有价值"。

---

## 阶段 5：现场演示③ 可扩展性（3 分钟）

### 5a. 现场加渠道

**敲**：

```bash
python -m credwatch new-source qichacha --label "企业信息平台" --category "内容共享平台"
python -m credwatch sources --health
```

**屏幕**：生成渠道骨架、自动注册、自动追加配置，渠道数 15 → 16。

**讲**：全程没改任何一行已有代码，只实现了一个 `discover()` 方法。

### 5b. 规则归纳

**敲**：

```bash
python -m credwatch induce-rule --name induced-qcc \
  --samples "qcc-eyJhbGciOiJIUzI1NiJ9.xxx,qcc-eyJhbGciOiJIUzI1NiJ9.yyy"
```

**屏幕**：归纳出公共前缀 + 长度区间 + 字符集 + 熵区间的候选规则，并做冲突检测。

**讲**：规则库最大的敌人是格式变化，机器起草 + 人工审核。

---

## 阶段 6：性能与合规（2 分钟）

**性能**：`python -m credwatch bench --documents 2000`——139 文档/秒、峰值 54 MB、
critical+high 召回 99.9%。强调"固定随机种子、可复现"。

**合规**：三条红线 + 只读验证白名单 + 默认不联网 + 明文不落盘。
这是"防御性题目"的底线，也是能过评审"有没有攻击性质"这一关的关键。

---

## 阶段 7：答疑预案（1 分钟 + 提问环节）

把评审大概率会问的问题提前备好答案：

| 可能提问 | 回答要点 |
| --- | --- |
| "和 gitleaks 区别？" | 见《对比优势与基准》：层次不同，我们是面向公开渠道的监测平台 |
| "发现数量可信吗？" | 指纹去重 + 占位符过滤 + 分级，数量经得起逐条核查 |
| "是不是套壳开源？" | 核心代码自研，规则文件未复制任何第三方，见《引用与开源组件说明》 |
| "误报率多少？" | 现场跑 `demo`，README 反例零命中；`lint-rules` 保证规则库健康 |
| "有攻击性质吗？" | 无，只读验证、默认关闭、白名单接口，见《合规与伦理声明》 |
| "怎么证明够快？" | MTTD 中位数 0.12 小时（demo），事件流订阅 + 增量游标 |
| "代码是你们写的吗？" | 现场打开任意源文件讲实现；Git 提交记录 + 规则库脚本可追溯 |

