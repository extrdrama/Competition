# 凭迹 CredWatch · 创新点说明

评审在"原创性与创新性"这一项上，最想看到的是**别人没有做、而且确实有价值**的东西。
本文档把这套系统的创新点逐条说清楚：它是什么、为什么必要、怎么实现、怎么验证。

---

## 创新性对照结论（基于 2026-09 调研）

对主流工具（TruffleHog、GitGuardian、gitleaks、CredSweeper、detect-secrets、
GitHub Secret Scanning）与学术文献（Meli NDSS'19、SecretBench MSR'23、
CredData、LLM 检测 arXiv'25）做了系统调研，完整矩阵见
《对比优势与基准》第一、二节。结论：

- **经调研未见同类实现的创新**：凭据对关联（组合风险）、逐特征可解释评分、
  误报反馈自校准闭环、规则自动归纳、明文不落盘的平台设计、
  国产生态格式覆盖（wxapkg / 微信支付 / 国产数据库连接串）；
- **承认差距并给出路线的**：检测器规模（194 vs TruffleHog 800+）、
  公开基准 F1 量化（SecretBench/CredData 评测已列入路线图，第六节）；
- **刻意取舍**：不采用 ML/LLM 检测——确定性规则+可解释概率让每条结论可审计，
  轻量 RNN 作为后续补强选项。
- **公开基准实测（已用数据验证）**：在 CredData 上以官方口径与 gitleaks v8.30.1
  **同子集对比**，凭迹优化后 **F1 0.3493 / 召回 0.2420 均高于 gitleaks
  （0.2935 / 0.1788）**；精度 0.6272 仍低于 gitleaks（0.8179），已列为后续优化重点。
  优化过程本身即"数据驱动"：4 项修复全部源自评测归因（详见《对比优势与基准》第六节）。

## 创新点 1：凭据对关联（组合风险分析）

### 为什么必要

绝大多数凭据扫描工具的输出是一条条**孤立的字符串**。但从攻击者视角看：

- 单独一个 AWS Access Key ID **无法利用**，必须配上 Secret 才能调用 API；
- 单独一个 OAuth Client ID 只是公开标识，配上 Client Secret 才能冒充应用；
- 单独一个 JWT 只是会话凭证，配上签名密钥就能**伪造任意身份**。

也就是说，**两条中风险凭据同时出现，实际风险高于任意一条严重凭据单独出现**。
这是 1 + 1 > 2 的组合风险，而现有工具（包括 gitleaks、trufflehog）普遍不做这层关联。

### 怎么实现

`credwatch/correlation.py` 定义了 9 类凭据对（云厂商 AK/SK、OAuth Client、JWT+签名密钥、
加密私钥+口令、支付宝/微信支付商户对等），在两个范围做关联：

| 范围 | 含义 | 可信度 |
| --- | --- | --- |
| `document` | 同一文件内成对出现 | 高（几乎必然同一次硬编码） |
| `origin` | 同一仓库/工程目录/镜像内成对出现 | 中（跨文件引用同样可用） |

命中后：整组成员风险等级**升级为 critical**，置信度上调，并在报告中给出
"该组合可直接被攻击者利用"的具体危害说明与处置优先级。

### 怎么验证

**真实渠道实测**：三轮独立扫描中，数字资产私钥（比特币 WIF、以太坊私钥）
与 OpenSSH 私钥被持续识别并升级为 critical（第三轮 46 个，见《测试报告》8.8）。
单元测试覆盖了"同文件配对""跨文件配对""不同仓库不误关联""单条不误报"四种边界。

## 创新点 2：可解释概率评分 + 权重自适应

### 为什么必要

传统扫描器给一个"分数"，但说不清这个分数怎么来的。评审问"这条为什么判为真"，
只能答"分数够了"。这既不利于答辩，也不利于调参——不知道哪个信号起了作用，
就只能靠拍脑袋改阈值。

### 怎么实现

`credwatch/detectors/scoring.py` 把判定改造成**特征向量 + 逻辑回归**：

1. **19 维特征**：左侧是否有敏感变量名、是否在 .env 里、值是否带已知前缀、
   熵是否够高、是否出现在文档路径里、邻近是否有哈希/校验值等；
2. **概率输出**：`p = sigmoid(w·x + b)`，输出直接读作"这是真实凭据的概率"；
3. **可解释**：返回每个特征的贡献量 `特征值 × 权重`，按影响力排序；
4. **权重可校准**：初始权重是安全工程师的专家先验，有了人工标注后，
   用带 L2 正则 + **先验锚定**的逻辑回归重新拟合。

"先验锚定"是防止小样本跑偏的关键——样本越少，先验的话语权越大。

### 怎么验证

演示脚本 `scripts/demo_feedback_loop.py` 在 15 条标注样本上把准确率从
**0.533 提升到 0.933**，精确率从 0.533 提升到 **1.000**。
报告中的每条发现都附有"判定依据"，答辩时可直接逐条讲解。

## 创新点 3：误报反馈闭环

### 为什么必要

任何扫描器都会误报。区别在于：**误报之后发生了什么**。

- 多数工具：用户只能把误报项从列表里删掉，下次照旧误报；
- 本系统：把误报标记为训练样本 → 重新校准评分权重 → 改变判定边界本身。

前者是"打补丁"，后者是"真的变聪明"。

### 完整闭环

```
标注（确认 / 误报，特征向量随标注入库）
  → 校准（逻辑回归 + 先验锚定，产出新权重）
  → 生效（下次扫描自动加载）
  → 抑制（已确认的误报指纹不再重复上报）
  → 复核（重扫确认修复结果）
```

对应的命令：`credwatch feedback`、`credwatch calibrate`、`credwatch verify`。

## 创新点 4：规则自动归纳

### 为什么必要

规则库最大的敌人是**格式变化**——新平台上线、老平台改 token 格式，手写规则永远追不上。

### 怎么实现

`credwatch/rule_induction.py` 从一批**已确认的泄露样本**自动归纳候选规则：

1. 提取公共前缀（`sk-`、`ghp_`、`LTAI`）；
2. 统计长度区间（样本足够时收紧到固定长度）；
3. 判定字符集（全大写+数字 / 字母数字 / 含符号）；
4. 计算熵区间（剔除纯数字串）；
5. 生成候选 YAML，并做**与已有规则的冲突检测**。

关键是"候选 + 人工审核"的定位：归纳是启发式的，可能过拟合少数样本，
它负责把写规则从"完全手工"变成"机器起草 + 人工审核"，而不是替人做决定。

### 怎么验证

`python -m credwatch induce-rule --samples "demo-xxx,demo-yyy"` 现场生成一条能命中
全部样本的候选规则，并自动报告与现有规则的重叠。

## 创新点 5：真实数据驱动的精度迭代

这是最能体现工程成熟度的一点，也是最容易被忽略的：**拿真实数据打自己的脸，然后修**。

我们的做法是先跑离线语料，再跑**真实公开渠道**（GitHub 公开 Gist，无需令牌），
对比两者的表现：

| 轮次 | 数据 | 结果 | 暴露的问题 |
| --- | --- | --- | --- |
| 第 1 轮 | 离线合成语料 25 份 | 30 个唯一凭据，反例零命中 | 合成语料太"干净"，掩盖了真实噪声 |
| 第 2 轮 | 真实 GitHub 数据 30 份 | 6 条命中，**全是误报**（包名 `com/xxx_x86`、构建标识 `PATCH_xxx`） | 熵检测无佐证也能到 0.83 |
| 第 3 轮 | 真实 Gist 120 份 | **715 条命中**，其中 707 条来自同一文件刷屏 | 缺命中风暴抑制；规则 `-p` 过宽命中内核路径 |
| 第 4 轮（修复后） | 同一批真实数据 120 份 | **57 个唯一凭据**（high 6），噪声受控 | — |

由此落地了三项机制，并**各自固化为单元测试**：

1. **熵检测佐证门控**：无敏感标识符/已知前缀/敏感文件佐证的熵命中一律拦截；
2. **规则收紧**：`docker-history-secret` 移除裸 `-p`，并排除以 `/` 开头的路径；
3. **命中风暴抑制**：同一文档内同一规则最多上报 50 条（按置信度保留），超出合并计数并标注。

这轮迭代的价值不在"修了三个 bug"，而在**证明这套系统具备"在真实数据上持续收敛"的能力**——
离线指标好看不算数，真实数据上能站住才算数。

## 创新点 6：渠道脚手架（可扩展性现场证明）

赛题评分项"平台可扩展性、新监控渠道的易扩展性"。光说架构灵活没有用，
要让评审**当场看到**。

```bash
python -m credwatch new-source 某平台 --label "某平台"
```

30 秒内生成：渠道实现骨架（只需填 `discover()` 一个方法）、自动注册到渠道注册表、
自动追加到配置文件。答辩时可现场演示"接入一个新渠道"。

架构上，新增渠道 = 继承 `SourceAdapter` 实现 `discover()`，
`normalize()`（含归档/镜像/小程序解包）与 `next_cursor()`（增量游标）由基类提供默认实现。

## 创新点 7：容器镜像"删了不等于没有"检测

这是渠道覆盖上容易被忽略、却危害最大的一类：

1. 镜像**分层**存储，某层写入过密钥，即使后面的层删掉文件，前面的层依然保留完整内容；
2. 镜像 config blob 的 **history 字段完整记录每层的构建命令**，
   `ENV SECRET_KEY=...`、`ARG TOKEN=...` 被原样保留。

因此本系统对镜像采集两类内容：`image_history`（构建历史，命中率最高）与
`image_layer`（逐层解包后的文件系统）。同时给出"构建期改用 BuildKit secret"的根因修复建议。

## 创新点 8：只读活性验证（自实现云签名）

把"疑似泄露"升级为"已确认可用"，是应急响应价值的关键。本系统实现了 16 个
只读验证器，其中 **AWS SigV4、阿里云 HMAC-SHA1、腾讯云 TC3-HMAC-SHA256 三种签名算法
均依据官方公开文档自行实现**，未使用任何云 SDK。

安全护栏（代码级强制）：默认关闭、全局限速、只读接口白名单；
没有统一只读入口的平台（华为云、Google API Key）明确返回"无法判定"，
不做猜测性判定。

## 创新点 9：可复现性能基准 + 规则库自检

- **性能基准** `credwatch bench`：固定随机种子生成语料，输出吞吐量、阶段耗时、
  规则热点、峰值内存，任何人可复现出同样的数字。
- **规则库自检** `credwatch lint-rules`：校验正则编译、ID 重复、`secret_group` 越界、
  验证器存在性、格式特异性，把"规则文件是数据，数据也要校验"落到实处。
